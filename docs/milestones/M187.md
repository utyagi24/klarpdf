# M187

## Design

### M187 — the bridge offers skills, as a trial (planned 2026-11-25)

On 2026-11-25 the owner asked what "Skills over MCP" is, and whether it could help the bridge. They
asked for the trial to be a milestone, because a follow-up in `PROGRESS.md` sometimes gets missed.
They also asked for the plan to include updating the MCP library, because the version the bridge
pins has no skills support.

**Surfaces: the bridge only.** The change is in `klarpdf/mcp_bridge/`, its tests and the bridge's
dependency locks. Nothing in `klarpdf/model/` or `klarpdf/util/` changes, and the app's Windows lock
does not include the MCP library, so the app is not reached.

#### What a skill is

A skill is a Markdown file of instructions for an agent, named `SKILL.md`. It starts with a name
and a one-line description. At first the agent sees only the name and the description. When a task
matches the description, the agent reads the whole file.

Until now, skills were files on the user's own machine. Skills over MCP lets a server ship skills
next to its tools:

- When the client connects, it asks the server for its list of skills (`skills/list`).
- It shows the model each skill's name and description.
- It reads a skill's full text only when the model asks for it.

It is an official MCP extension, `io.modelcontextprotocol/skills`. Its proposal,
[SEP-2640](https://modelcontextprotocol.io/seps/2640-skills-extension), is marked final. It needs
protocol version 2026-07-28. The skill files are ordinary MCP resources, at addresses that start
with `skill://`.

The difference from a tool description: a description says what one tool does. A skill says which
tools to use for a task, in what order, and what rules apply.

#### Where it works today

Checked on 2026-11-25 in Anthropic's [Claude Code MCP docs](https://code.claude.com/docs/en/mcp)
and its [announcement](https://claude.com/resources/articles/skills-over-mcp-tasks-and-more),
unless another source is named.

- **Claude Code** has it as a public beta from v2.1.331. It also needs a recent model: a Fable
  model, Claude Opus 4.8, Sonnet 5, Haiku 5.5 or later.
- **Plans.** It is on by default for Pro, Max and Ultra. On Team and Enterprise it is off until an
  admin turns it on. With an API key it is off for now. (The announcement says Enterprise is
  "coming soon". The docs say an Enterprise admin can turn it on.)
- **Where in Claude Code.** The terminal, local sessions in the Desktop app's Code tab, and VS Code,
  where it is still rolling out.
- **Not supported:** `claude -p`, the Agent SDK, cloud sessions, Claude Desktop extensions and
  servers listed in `claude_desktop_config.json`. Our Claude Desktop package is a Desktop extension
  (the `.mcpb` file), so Claude Desktop users get nothing yet.
- **Other clients.** VS Code with GitHub Copilot has it on by default from version 1.147, according
  to [one vendor's article](https://dev.to/netnose/skills-over-mcp-the-server-brings-its-own-instructions-4d3n).
  The same article says Codex and ChatGPT have it planned. SEP-2640 lists a Gemini CLI prototype.
- **What the user sees in Claude Code.** A server's skill shows as `<server>:<skill>`, so ours
  would be `klarpdf:<skill>`. The user can type `/klarpdf:<skill>`, or Claude loads it on its own.
- **Asking first.** In auto mode a classifier decides whether a skill loads, with no prompt. In the
  manual modes Claude Code asks, and "Allow this version" lasts until the server changes the
  skill's files.
- **Limits.** Up to 100 skills per server, 100 KB per text file, 400 KB per skill. All of the
  bridge's tool text today is about 85 KB (`docs/milestones/M179.md`), so these limits do not
  matter here.
- **What Claude Code ignores.** Front-matter fields such as `allowed-tools` and `hooks`, `!`
  commands and `@` references ([skills docs](https://code.claude.com/docs/en/skills)).

#### What it could do for the bridge, and what it cannot

It could:

- **Describe tasks that use several tools in order.** No single tool description holds that today.
- **Take text out of the instructions.** Every session pays for the instructions in full
  ([M180](M180.md), the bridge's cost to every session). A skill costs only its name and
  description until it is used.
- **Say the batch-edit rules once.** [M181](M181.md) (several edits to one document in one call)
  asks, in its open question 3, whether each step tool's description should mention the batch.
  Each mention costs characters in descriptions near the 1,900-character limit that
  [M105](M105.md) set.

It cannot:

- **Replace text Claude needs before a call.** A skill loads only when Claude decides the task
  matches. The [Agentic AI Foundation's write-up](https://aaif.io/blog/skills-over-mcp) says models
  "often ignored available skills and tried to use tools directly", and that adherence declines as
  the context grows.
- **Reach clients without support.** Those never see it.
- **Do anything a tool does.** A skill is text. It cannot write one file instead of three, or check
  a redaction.

So this milestone tries it, and measures it, before anything depends on it.

#### What the trial must answer

1. Does Claude Code load the skill on its own, when a task matches and the user does not name it?
2. Once loaded, does Claude follow it?
3. How much does it add to every session?

#### The parts

One PR per part.

**M187.1 — update the MCP library to the first release with skills support.** *Waits for that
release.*

- The pinned library, `mcp` 2.3.0 with `mcp-types` 2.3.0, has no skills support. The library's
  skills support was merged on 2026-10-11
  ([python-sdk #3485](https://github.com/modelcontextprotocol/python-sdk/pull/3485)), nine days
  after 2.3.0 came out. Checked on 2026-11-25: 2.3.0 is still the newest release on PyPI. So this
  part waits for the next release that has it.
- What the merged change adds, from its description:
  - a ready-made `Skills` extension for a server (`mcp.server.skills`). It answers `skills/list`,
    `skills/get` and the optional directory listing, and declares the extension when a client
    connects;
  - a check of every reply against SEP-2640 before it is sent: the name, the address, the front
    matter, the digest format and the file list;
  - matching calls for a client (`mcp.client.skills`), and a function that checks a file's size
    and digest against the list. The bridge's tests can use them.

  It does not find skill files, build the list or decide how long a client may keep it. The
  bridge does that.
- The update changes `mcp` and `mcp-types` and nothing else. Skills come in M187.2.
- Follow `RELEASE.md` §1 (change a dependency). The library is pinned in the bridge's lock
  (`requirements-mcp.in` and `requirements-mcp.txt`) and in the dev lock (`requirements-dev.txt`).
  Three more files follow from the bridge's lock: the pins in the root `pyproject.toml`
  (`packaging/mcp/pypi/sync_pins.py`), the `.mcpb` build's `pyproject.toml`
  (`packaging/mcp/mcpb/build_mcpb.py`), and that build's `uv.lock` (`uv lock` in
  `packaging/mcp/mcpb/`). The app's Windows lock does not include the library, so the app is not
  reached.
- **Read the release notes of every version after 2.3.0.** The update from 2.0.0 to 2.3.0 changed
  how a tool's error reaches the agent, and ten bridge tests failed until the bridge changed
  ([M162](M162.md), the audit passes again on `mcp` 2.3). Run the whole bridge suite, and the full
  suite if the update moves a library the app shares. Check one refused call over a real stdio
  connection, as M162 did: the agent still gets the reason, and the server's stderr stays empty.
- Check that the new release supports every Python the bridge supports (`requires-python` is
  `>=3.11,<3.15`, [M132](M132.md)).
- Run `pip-audit` on the changed locks (`invoke audit`).

**M187.2 — serve skills, with one skill: reading a long PDF without wasting steps.** *Needs M179
and M187.1.*

- The bridge passes the library's `Skills` extension to the server, next to the one it already has
  for refusing a misspelt argument (`StrictArguments`, [M106](M106.md)).
- Each skill is one file, `klarpdf/mcp_bridge/text/skills/<name>/SKILL.md`, in the folder that
  [M179](M179.md) (all the bridge's text in one folder) sets up. Its front matter has `name` and
  `description`, and `name` equals the folder's name.
- The server reads every skill once, when it starts, as M179 does for the tool files. It refuses to
  start, with an error naming the file, if a skill has no front matter, has no `name` or
  `description`, or has a `name` that differs from its folder.
- A skill is served at `skill://klarpdf/<name>/SKILL.md`. The list gives each file's size and
  SHA-256 digest, worked out from the bytes the server sends. No skill is listed as `"dynamic"`,
  because a client may refuse to load one
  ([Microsoft's write-up](https://techcommunity.microsoft.com/blog/azure-ai-foundry-blog/delivering-agent-skills-over-mcp/4562722)).
- A skill holds text only, with no scripts. See *Rejected*.
- The `--read-only` build serves a skill only if it serves every tool the skill names. It already
  lists a tool's documentation page only when it serves the tool (`publish_docs` in
  `klarpdf/mcp_bridge/server.py`). A test reads each skill and fails if it names a tool that the
  build does not register.
- **The first skill** tells Claude how to read a long PDF without wasting steps. It expands the
  instructions' paragraph on using the cheap tools first:
  - `get_info` first: the page count, whether there is a text layer, whether the file is encrypted.
  - `get_outline`, `get_heading_candidates` and `search` to find the part that matters.
  - `extract_text` on those pages only.
  - `get_tables` for tables.
  - `render_page` only when the text cannot answer: scans, figures, layout, signatures.
  - A reply with `truncated: true` means the request was too wide. Narrow it.

  It is the first because it is advice, not a safety rule. If Claude skips it, nothing goes wrong.
  The instructions keep their paragraph during the trial, so a client without skills loses
  nothing.
- **Ship the file.** M179.1's packaging tests check that the text folder is in the wheel, the
  source package and the `.mcpb` bundle. Make sure they cover the new skill file. The `.mcpb`
  bundle carries it even though Claude Desktop does not use it yet.
- **Tests,** in a new `tests/test_mcp_skills.py`, against the live server, using the library's
  client calls:
  - The server declares the extension.
  - `skills/list` gives each skill's address, its front matter as written in the file, and each
    file's size and digest. The size and digest match the bytes `resources/read` returns.
  - `skills/get` gives the same entry. An address the server does not serve is refused with
    `-32602` (invalid parameters).
  - The `--read-only` build serves only the skills whose tools it serves.
  - A client that does not ask for the extension sees the same tools, resources and instructions
    as before.
  - Break each check on purpose and watch it fail: change one byte of the served text after the
    list is built, and rename a skill's folder so it differs from its `name`.
- **Measure the cost.** The skill's name and description go into every session in Claude Code.
  If M180.1 (measure what each client loads) is built by then, its limit for what every session pays
  counts them, and this PR raises the limit with the owner's go-ahead. If not, this PR records the
  size, and M180.1 counts it when it is built.

**M187.3 — try it by hand in Claude Code, and record what happened.**

The test suite cannot see whether Claude loads a skill, or whether it follows one. Only a real
session can. This part changes no code, unless the trial shows the skill's text needs it.

- Before the first run, write down the tasks and, for each one, the calls a good run makes. Use
  real documents from the corpus that need several steps: a long report with an outline, one with
  tables, a scan. The results are compared with these written expectations, not only with each
  other (CLAUDE.md, *Fix a class of bug once*).
- The owner runs Claude Code v2.1.331 or later on a plan that has skills over MCP turned on.
  - `/mcp` shows protocol 2026-07-28 for the bridge. If it shows no protocol row, the Claude Code
    docs' troubleshooting section says what to check.
  - `/klarpdf:<skill>` appears when the owner types `/`.
  - `/context` shows what the skill's name and description add.
- Run each task in a fresh session, without naming the skill. Record whether Claude loaded the
  skill, and the calls it made.
- Run the same tasks once more with one sentence added to the instructions that names the skill.
  The Agentic AI Foundation's write-up says such a sentence helped. It costs characters in every
  session, so it stays only if it changes what Claude does.
- Check that the bridge still works where skills are not supported: Claude Desktop with the `.mcpb`
  bundle, and `claude -p`.
- Record the results in this file's `## Progress`.

**M187.4 — a second skill: several edits to one document in one call.** *Only if M187.3 shows that
Claude loads the first skill on its own. Needs M181.*

- The skill says once: for several changes to one file, use M181's tool; delete or reorder pages in
  a separate call, before or after it; put `flatten` last; preview a redaction with `search` first;
  check the result afterwards.
- It answers M181's open question 3 for clients with skills. M181's tool description still carries
  the rules Claude needs before it calls the tool, because a client without skills, or a Claude
  that skips the skill, needs them there.
- The same tests as M187.2 for the new file, and the same hand check as M187.3 on tasks with
  several edits.

#### After the trial

The owner decides from what M187.3 records. The choices:

- **Keep the skills.** Build M187.4.
- **Move text out of the instructions into a skill.** Only once the clients the owner uses support
  skills, including Claude Desktop. Until then a client without skills would lose the text.
- **Remove the skills,** if Claude does not load them on its own. Record why in this file, so the
  question is not argued again. The library update (M187.1) stays.

#### Order

- **M187.1 needs a release of the library with skills support.** It needs nothing else in the
  repo, so it can be built as soon as that release is out, before or after M179.
- **M187.2 needs M179 and M187.1.** The skill files go in M179's text folder, and M179.1's start-up
  checks and packaging tests are what M187.2 extends. Built before M179, the files would have to
  move.
- **M187.4 needs M181.** It describes M181's tool.
- M187 does not need M180. If M180.1 is built first, M187.2 updates its size limit. If M187.2 is
  built first, M180.1 counts the skill when it sets the limit.
- The OCR milestones (M182–M185) and files as tabs (M186) are separate roadmaps. M187 does not
  wait for them.

#### Open questions, for the owner in review

1. Is "reading a long PDF without wasting steps" the right first skill?
2. M187.4 is planned only if the trial works. Should it be planned now regardless?
3. If the library has no release with skills support by the time M179 is done, should the trial
   wait, or should the bridge answer the skill requests with its own code on 2.3.0? 2.3.0 has the
   general way to add an extension that the library's own `Skills` extension is built on. The cost:
   code that the next library update replaces, and checks against SEP-2640 the bridge would write
   itself.

#### Rejected

- **Skills that carry scripts** (2026-11-25). The bridge's safety rules hold only for calls through
  its tools: a write never touches the input file, and a redaction is checked before it reports
  success. A script would run outside those checks. Claude Code also warns that skills can direct
  Claude to run code, and SEP-2640 says a client must ask the user before running a skill's code.
- **Putting a rule Claude needs before a call only in a skill** (2026-11-25). A skill loads only
  when Claude decides the task matches, and models often skip skills. So the rules on writing files
  and on redaction stay in the tool descriptions and the instructions, as [M180](M180.md)'s rule
  already says.
- **A tool that returns guidance text, instead of the extension** (2026-11-25). The client would not
  list it as a skill, so Claude would not see its description in the skill list. The bridge already
  has resource pages for longer text (`klarpdf://docs/{tool}`, [M105](M105.md)).
