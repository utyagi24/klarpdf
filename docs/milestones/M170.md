# M170

## Design

### M170 — defects that hide (built 2026-11-10)

**Surfaces:** core, bridge, app, tests and tools. One change is visible to a user: the bridge's
`get_annotations` now names a grey or CMYK colour correctly (below). Everywhere else, behaviour
changes only if our own code is wrong.

**What Ruff now refuses** (`[tool.ruff.lint]` in `pyproject.toml`): bugbear (`B`), an `except`
that catches every error (`BLE001`), one that drops it with `pass` or `continue` (`S110`, `S112`),
and Pylint's errors and warnings (`PLE`, `PLW`), as planned. One rule was added that the plan did
not list: `RUF007`, which asks for `itertools.pairwise` where a list is paired with itself one
along. Without it, `B905` pushes a neighbour pair towards `zip(strict=True)`, which fails on every
call, because the two sides always differ by one. `RUF007` had five findings, all converted. The
`external = ["BLE001"]` line M168 added is gone. The five `noqa: BLE001` comments left in the core
are all still needed, so `RUF100` reports none of them.

The plan measured 124 findings, and there were 124.

**The owner's three decisions, in this session.**

1. **When two lists walked together differ in length, stop with an error.** Before, `zip` stopped
   at the end of the shorter list and the rest was skipped without a sign.
2. **An `except` that catches every error stays, with a reason**, except where Python lists the
   errors that can occur.
3. **A grey or CMYK colour is converted to RGB, then named.**

**The `zip` calls (45).**

* **5 pair each item with the next** (`zip(x, x[1:])`), so the two sides differ by one on purpose.
  They are `pairwise(x)` now, which says so. Four are in `tables.py` and `pdf_view.py`, one is in a
  test. `RUF007` found four. It missed `tables.py`'s `zip(found.bounds, found.bounds[1:])`, which
  a search of the tracked files found.
* **38 have `strict=True`**: 15 in `klarpdf/`, 4 in the app, 16 in tests and 3 in tools. In shipped
  code, each pairs lists built to the same length, or checks the lengths just above. So none can
  raise unless the code around it is wrong. Nothing changes for a user.
* **2 keep skipping, with `strict=False`.** `tools/table_corpus_check.py`'s `diff` compares two
  runs, which may find different numbers of tables and rows. The line above prints both lists in
  full, so the detail below covers only what both runs have.
* **One test fixture relied on the shorter list.** `_grid` in `tests/test_mcp_tables.py` paired
  the three vertical lines of a two-column grid with each row's two cells, so the right-hand line
  was skipped. It pairs the cells with `xs[:-1]` now. The three tests that use it failed with
  `strict=True` until then, and pass after.
* **The corpus checker could pair the wrong words.** Its `word_check` reads the page's words
  twice, with and without small glyph heights, and zipped the two lists by position. If the counts
  ever differed, every word after the first difference would be paired with another word.
  `tables._page_inventory` guards against this by using one list for both, and the checker now does
  the same.

**The colour defect `get_annotations` hid.**

* **What a user does:** asks the bridge for the marks in a document that someone highlighted in
  another program, and filters on `color_name`.
* **What they expect:** each mark named as the colour it is drawn in, or no name.
* **What they got:** a PDF colour has one value (grey), three (RGB) or four (CMYK, printing ink).
  The colour distances `zip`ped the stored values against three RGB channels. A grey has one value,
  so only red was compared. CMYK had its first three values read as RGB.

  | Stored colour | Mark type | Named before | Drawn as (RGB) | Named now |
  |---|---|---|---|---|
  | grey `0.5` | highlight | Blue | 0.5, 0.5, 0.5 | none |
  | grey `0.2` | underline | Blue | 0.2, 0.2, 0.2 | none |
  | CMYK `1 0 0 0` (cyan ink) | underline | Red | 0.0, 0.68, 0.94 | none |
  | CMYK `0 0 1 0` (yellow ink) | highlight | none | 1.0, 0.95, 0.0 | Yellow |
  | CMYK `0 1 1 0` (red ink) | underline | none | 0.93, 0.11, 0.14 | Red |

* **The fix** is `markup_palette._as_rgb`. It converts grey and CMYK through MuPDF's own colour
  conversion, the one that draws the page, before naming. PDF's simple formula (red =
  1 − min(1, C + K)) was measured and rejected: MuPDF manages colour by default, and draws CMYK
  `0 1 1 0` as 237, 28, 36 rather than the formula's 255, 0, 0. A one-pixel conversion matches the
  drawn page to within 1/255 for every colour tried. A colour with any other number of values gets
  no name. `color_exact` is always false for grey or CMYK, because the app writes only RGB.
  `color` still reports the values as stored. `klarpdf://docs/get_annotations` says all three.
* **Why `strict=True` alone was not the fix:** it would have turned the wrong name into an error,
  and that error would have failed the whole listing for one foreign mark.
* **Surfaces.** The change is in the core, but only the bridge calls `nearest_name` and
  `is_palette_color`. The app imports the palette's swatches and never names a colour. Tests on
  both sides: `tests/test_markup_palette.py` for the core, and `tests/test_mcp_annotations.py`
  through `get_annotations`.
* **Verified by breaking it.** Going back to the old code (no conversion, `zip` without `strict`)
  failed both test files: grey came back "Blue", and yellow ink got no name. Converting by the
  formula instead failed the test that compares the conversion with a drawn page, for each of the
  four CMYK colours.

**The 25 `except` clauses that catch every error, and the 5 that drop it** (`S110`, `S112`; all
five are among the 25).

* **23 are kept, each with its reason** in the `# noqa: BLE001 — why` form. Four of them drop the
  error with `pass`, so they name `S110` too. Most wrap a PyMuPDF call, and PyMuPDF does not list the
  errors it raises. If they were narrowed, an error nobody listed would stop the action partway or
  close the window, instead of showing a blank page or a message.
* **2 are narrowed**, where the errors are known:
  * `platform_integration.single_instance_server_name`, around `getpass.getuser()`. It now catches
    `OSError`, `ImportError` and `KeyError`. Python 3.13 raises `OSError` when the environment names
    no user. Python 3.12, which the app is built with, fails its password lookup with `ImportError`
    on Windows and `KeyError` elsewhere (read from 3.12's `getpass` source).
    `tests/test_single_instance.py` checks all three. With `except OSError:` alone, the
    `ImportError` and `KeyError` cases failed.
  * `tests/test_redaction_orphans.py`, around `xref_get_key`. It now catches only
    `fitz.mupdf.FzErrorBase`, MuPDF's own error. A free slot reads `null` without raising. This
    was the `S112` finding, which Ruff makes only for a catch-all.
* **The installer's `venv.create` stays broad, which differs from what this session first
  proposed.** Its errors are not documented after all: besides `OSError` and ensurepip's
  `CalledProcessError`, 3.12's `venv` raises `ValueError` in three places, one of them a path that
  contains the PATH separator. So it keeps catching everything and turns it into the installer's
  one-line message. It now raises that message `from exc`. Ruff then treats the clause as passing
  the error on, so it needs no `noqa`.

**The rest (49).**

* **4 lambdas in `main_window.py` must stay** (`PLW0108`). Ruff suggests replacing
  `lambda: self._paste_pages()` with `self._paste_pages`. That would create a bug: a menu item's
  `triggered` signal passes a `checked` flag, and PySide6 hands it to any method that can take an
  argument. `_paste_pages(before_index=None)` would get `False`, which counts as 0, so Paste Pages
  would always paste before page 1 (measured with a bare `QAction`). Cut, Copy and Duplicate Pages
  have the same shape. Each keeps its lambda, with a reason, and a comment above them explains why.
  The 3 needless lambdas in tests are gone.
* **11 `subprocess.run` calls name `check=`.** Ten read the exit code themselves, so they say
  `check=False`. The eleventh, `pdftotext` in `tests/test_search_redact.py`, used the output without
  looking at the exit code: if `pdftotext` failed, its first assertion would have passed on empty
  text. It says `check=True` now.
* **7 loops reassigned their own variable** (`PLW2901`), each on purpose: a stripped line, a
  trimmed entry, a rotated box. Each now keeps the original under the loop's name and gives the new
  value its own.
* **5 closures used a loop variable** (`B023`). Each was called only within the same pass, so none
  was wrong. `tables._divide`'s `run` takes `subs` as an argument now, and the test lambdas
  bind `seen` when they are made.
* **6 `raise` statements inside an `except`** (`B904`), all in the installer. The venv one is above.
  The other five replace the error with a message on purpose, so they say `from None`. The
  installer prints the message without a traceback, so nothing on screen changes.
* **4 `global` statements** (`PLW0603`) stay, with reasons: the Windows mutex handle and Qt's
  previous message handler are process-wide, and `tools/mcp_stdio_check.py` keeps a running tally.
* **5 unused loop variables** (`B007`) were renamed or dropped, and `pytest.raises(Exception)`
  (`B017`) became `pytest.raises(dataclasses.FrozenInstanceError)`. A test default of
  `QPoint(200, 200)` (`B008`) became a module constant. `viewer/form_fill.py`'s `_UNCHECKED` listed
  both `False` and `0`, which are one set member (`B033`), so `0` went and a comment says why. A
  nested `min` (`PLW3301`) became two lines.

**Seen in passing, and fixed here.** Three tests in `tests/test_markup_style.py` built widgets
without the `qapp` fixture, so they worked only after another test had made the Qt application.
Run alone, with `-k`, Python aborted. Unchanged `main` aborts the same way. Each now asks for
`qapp`, and each passes alone.
