# M179

## Design

### M179 — all the bridge's text in one folder, one file per tool (planned 2026-11-22)

The owner asked for this on 2026-11-22, while reviewing the `annotate` tool's text. Today a tool's
text is split across two Python files. Its resource page is put together only while the server runs.
So no file shows what an agent actually reads. The owner's words: "any reviewer should have a
dedicated single source of truth for the tool documentation", and "I prefer all user and agent
facing documentation to be consolidated".

**Surfaces: the bridge only.** The change is in `klarpdf/mcp_bridge/`, in the bridge's packaging
(`pyproject.toml`, the `.mcpb` build script and its `manifest.json`) and in the tests. Nothing in
`klarpdf/model/` or `klarpdf/util/` changes, so the app is not reached.

#### Where the text is today

Measured on `main` at `e6892f3`.

| Text | Where | How many |
|---|---|---|
| Tool descriptions | Docstrings in `klarpdf/mcp_bridge/server.py` | 23 |
| Reference pages, the part of `klarpdf://docs/{tool}` after the description | `klarpdf/mcp_bridge/docs.py` | 8 |
| The instructions, the general text an agent gets when it connects | `server.py`, four pieces joined into a normal and a read-only version | 1 |
| The heading at the top of every resource page | `server.py`, in `_documentation` | 1 |
| The names and one-line summaries in the list of resources | `server.py`: the docs template, each tool's page, the environment page | 3 kinds |
| The short summary of each tool that Claude Desktop shows | `packaging/mcp/mcpb/manifest.json` | 23 |
| Claude Desktop's short and long description of the bridge | `manifest.json` | 2 |

The tool descriptions and reference pages together are 86,292 characters.

#### Decisions (owner, 2026-11-22)

1. **One folder, `klarpdf/mcp_bridge/text/`.** Each tool has one Markdown file in `text/tools/`,
   named after the tool, such as `text/tools/annotate.md`. The text that is not about one tool is
   in `text/server.md`.
2. **A tool's file has up to four parts,** each under a top-level heading, in this order:
   - `# Summary`: one line. Claude Desktop shows it in its list of tools (M179.3).
   - `# Description`: sent to the agent as the tool description. Every file has one. It stays
     within the 1,900-character limit that M105 set.
   - `# Parameters`: one line for each parameter (M179.4). It is not sent in the description.
   - `# Reference`: the rest of the resource page. Only tools that need one have it.

   The resource page is the shared heading, then the description, the parameters and the
   reference. The description is read once and used in both places. It is not stored twice.
3. **The server reads every file once, when it starts.** The text is not copied into the code at
   build time. See *Rejected*.
4. **The files are not compressed.** See *Rejected*.
5. **Each tool's parameters are listed in its file,** for people and agents who read the file. The
   list stays out of the tool description: the agent already gets each parameter's name, type and
   default from the input schema, and the description has a size limit. **The resource page
   includes the list.** It is the only place an agent can read what each parameter means. A test
   keeps the list in step with the schema.
6. **`klarpdf/mcp_bridge/README.md` and `QUICKSTART.md` stay as they are.** They are already
   Markdown files, and they keep their own wording about the tools.
7. **Text the code writes during a call stays in the code.** This list was proposed on
   2026-11-22, and the owner did not ask to move any of it:

   | Text | How many | Why it stays |
   |---|---|---|
   | Error messages a tool returns when it refuses a call | 92: 70 in the bridge, 22 in the core | Each fills in values from the call, such as a page number or a key name. Each sits next to the check that triggers it. The core's are shared with the app. |
   | Warnings and notes in a reply | 28 places in the bridge | The same reasons. |
   | `klarpdf-mcp --help` | 3 lines | It is part of the program's command-line handling. |
   | What `install.py` prints | 22 lines | The installer is one file that runs before the bridge is on the machine. |
   | The one-line summary on PyPI | 1 | It is package information in `pyproject.toml`, where the packaging tools read it. |

   The counts come from searching the code, and are approximate.

#### The parts

One PR per part. Build in number order. All four parts come before M180: see *How this fits with
the other planned work*.

**M179.1 — move each tool's description and reference into its file.** The wording does not change.

- Make `text/tools/<tool>.md` for all 23 tools: a `# Description` part, and a `# Reference` part
  for the 8 that have one.
- When the server starts, it reads every file and registers each tool with the description from
  its file (`server.tool(description=...)`). The function keeps no docstring for agents. A comment
  names its file.
- Remove `docs.py`. `_documentation` builds the resource page from the file.
- The server refuses to start, with an error naming the file, when a tool has no file, a file
  has no tool, a file has no `# Description`, or a heading is unknown or out of order. A line
  inside a fenced code block is never a heading.
- **Ship the files.** A Markdown file added under `klarpdf/mcp_bridge/` is left out of the PyPI
  package today (tested 2026-11-20 with `uv build`). `pyproject.toml` lists the folder as package
  data. The release builds two packages with `python -m build`: the wheel, and a source package that
  some machines build themselves (`.github/workflows/publish-pypi.yml`). A test builds both and
  checks that every file is in each. A second test runs the installed bridge from outside the
  checkout and reads one description and one resource page. The `.mcpb` build copies the folder,
  but it drops any file called `README.md`, so no file may have that name. A test checks the built
  bundle.
- **Check that the text did not change.** Before the move, save each description and resource page
  as the server sends them. After the move, compare them byte for byte. Change one character in one
  file on purpose, and watch the check fail.
- The checks in `tests/test_mcp_docs.py` keep reading the live server. The ones that import
  `docs.REFERENCE` read the files instead.
- Update the text that describes the old layout: `PLAN.md` §Architecture (the paragraph naming
  `docs.py`), `PLAN.md`'s lint table (the `E501` exception for `docs.py`), the CLAUDE.md gotcha on
  MCP descriptions, and `docs/why-the-rules.md` §MCP descriptions.
- Measure how long the server takes to start, before and after.

**M179.2 — move the text that is not about one tool into `text/server.md`.**

- The four pieces of the instructions. The server joins them for the normal and the read-only
  versions, as it does today. The file writes `klarpdf://env` out in full. A test checks that it
  names the environment page the server registers.
- The heading at the top of every resource page.
- The names and one-line summaries in the list of resources: the docs template, each tool's page
  (with the tool's name filled in), and the environment page.
- The same before-and-after check as M179.1.

**M179.3 — Claude Desktop's text comes from the files.**

- Each tool's summary moves from `manifest.json` to the `# Summary` part of its file. Claude
  Desktop's short and long description of the bridge move to `text/server.md`.
- `packaging/mcp/mcpb/build_mcpb.py` writes them into the bundle's `manifest.json`, as it already
  writes the version. The copy of `manifest.json` in the repo no longer holds them.
- This is the one place where text is copied at build time. Claude Desktop reads the manifest
  before the server starts, so the server cannot supply it.
- `test_the_manifest_lists_every_tool_the_server_registers` in `tests/test_mcp_packaging.py`
  checks the built manifest instead. A new test checks that each summary there equals its file.

**M179.4 — each tool's file lists its parameters.**

- Add a `# Parameters` part to all 23 files. For `annotate`:

  ```markdown
  # Parameters

  - `path` (string, required): the PDF to mark up. It is never changed.
  - `marks` (array of objects, required): the marks to write. The keys of a mark are in the description.
  - `out` (string, required): where to write the new file.
  - `password` (string or null, default null): the password, if the file needs one.
  - `overwrite` (boolean, default false): replace `out` if it already exists. The input is never replaced.
  ```

- Types are in the words the schema uses: string, boolean, array of objects, string or null.
- The resource page shows the parameters between the description and the reference.
- A test compares each file's list with the live schema: the names, the types, which are required
  and the defaults. It fails on a parameter that is missing, extra or different. Break it on
  purpose by renaming one parameter in the code.
- The description still explains what the schema cannot. The schema says only that `marks` is an
  array of objects, so the keys of a mark stay in the description.
- The line of meaning for each parameter is new writing for 23 tools. The owner reviews it.
- Nothing is added to the descriptions, or to anything else an agent gets when it connects. So the
  1,900 limit does not move.

**The order.** The owner asked on 2026-11-23 that the milestone numbers follow the order of
building. Nothing was merged yet, so the three were renumbered: the `annotate` fix became M178,
this plan M179, and the plan for less room in sessions M180.

1. M178 (PR #470).
2. M179.1 to M179.4.
3. M180.1 to M180.5, and M180.6 if it is needed.

An earlier draft put M180.1 to M180.3 between M179.3 and M179.4, so that each parameter list would
be written once. With the numbers in building order, M179.4 comes before M180.3. The cost: if
M180.3 writes optional parameters as a plain value, it also rewrites their type words in the
parameter lists. There are 37 optional parameters (`docs/milestones/M180.md`).

#### Rejected

**Copying the text into the code at build time** (the owner's first idea, 2026-11-22). Then the
Markdown files need not ship, and the package holds one copy. But every way of building or running
the bridge from the repo must run the copying step first: the tests and development, which run
from the repo folder; the PyPI wheel; the PyPI source package, which some machines build
themselves; and the `.mcpb` build. Any route that misses the step starts with old text or with no
descriptions. Reading at start-up needs no step. The owner agreed on 2026-11-22.

**Reading each file only when it is needed.** The descriptions are needed when an agent connects,
since the server sends them all in one reply. A broken reference part would stay hidden until an
agent asked for that page in the middle of a task. And a running server could mix the text of two
versions after an upgrade. The cost of reading at start-up, measured on WSL:

| What | Time |
|---|---|
| Starting Python and loading the bridge's code, today | 746 ms |
| Setting up the server and its 23 tools, today | 31 ms |
| Reading 23 files holding all of today's tool text, already in memory | 0.13 ms |

**Shipping the files compressed.** The text is 85 KB, and 31 KB once compressed. The PyPI package
and the `.mcpb` bundle are zip files, so the text is already compressed for download. For
comparison, the PyPI package is 350 KB, the bridge's own code is 837 KB, and PyMuPDF installed is
62 MB. GitHub cannot show a compressed file, and a PR cannot show what changed in it.

**Two files per tool**, one for the description and one for the reference. The owner asked for
one file per tool.

**Keeping the text in Python, with a saved copy of what agents receive** (proposed 2026-11-22). A
test would keep the copy in step. It leaves two copies of the text, and the owner chose one source.
