# M181

## Design

### M181 — several edits to one document in one call (planned 2026-11-23)

The owner asked on 2026-11-23 how to stop a chain of edits from leaving a trail of files. Every
write tool reads one file and writes a new one. So a caller who fills a form, highlights two
passages and redacts a name makes three calls. That leaves two in-between files. If the redaction
is not the last call, those files still hold the name. [M100](M100.md) called this a problem our
own design causes, so it is ours to fix rather than the caller's to remember.

Several tools already take many edits of their own kind in one call:

- `annotate` takes many marks ([M101](M101.md)).
- `redact_text` takes many search terms ([M100](M100.md)).
- `redact_regions` takes many regions.
- `fill_form` takes many fields.
- `rotate` takes many pages.

What is missing is one call that combines different tools.

**Surfaces: the bridge only, as planned.** The new tool lives in `klarpdf/mcp_bridge/`. It uses the
core the way the app already does. The app makes many edits to one `VirtualDocument` (the in-memory
list of pages and edits, `klarpdf/model/virtual_document.py`) and writes once when the reader saves.
If the build finds that the core must change, that change also owes tests in the app (CLAUDE.md,
*Two consumers share one core*).

#### Decisions (owner, 2026-11-23)

1. **One new tool takes a list of steps.** There is no mode that keeps a document open between
   calls. See *Rejected*.
2. **Only tools that edit one document can be steps.** `merge`, `split`, `extract_pages` and
   `export_images` read or write several files, so they are not steps.
3. **No step may change the order of the pages.** `delete_pages` and `reorder` are not steps. So a
   page number means the same page in every step.

Decision 3 has a second effect. With no page moved, every batch edits a copy of the original file.
A rotation does not count as a page move (`VirtualDocument.page_set_unchanged`). So the output keeps
the accessibility tags, the encryption and everything else the file holds outside its pages, as
`fill_form` and the redactions do today. The reply never has to warn that these were lost.

#### The tool

Its working name is `edit`. The owner may choose another name when it is built.

```json
{"path": "lease.pdf", "out": "lease-final.pdf", "steps": [
  {"tool": "fill_form", "values": {"Tenant": "A. Smith"}},
  {"tool": "annotate", "marks": [{"type": "highlight", "page": 2, "boxes": [[72, 300, 240, 312]], "note": "check this date"}]},
  {"tool": "redact_text", "queries": ["607347469"]},
  {"tool": "rotate", "degrees": 90, "pages": [5]}
]}
```

- `path`, `out`, `password` and `overwrite` belong to the call, as in every write tool. A step does
  not take them.
- A step names its tool and gives that tool's own arguments.
- These tools can be steps: `fill_form`, `annotate`, `redact_text`, `redact_regions`,
  `set_outline`, `rotate` and `flatten`.
- `flatten` can only be the last step. After it, no form fields or marks are left to edit.
- The steps run in the order given. Each step sees the result of the steps before it, as separate
  calls do.
- The call writes one file. If any step fails, it writes nothing, and the error names the step by
  its number.
- The redaction check runs once, on the file the call wrote, after every step has run. A redaction
  step reports success only if that check passes, as `redact_text` and `redact_regions` do today.
- An argument a step does not accept is an error, as [M106](M106.md) made it for every tool. This
  includes a misspelled key inside a step. [#468](https://github.com/utyagi24/klarpdf/issues/468)
  is a key inside an `annotate` mark that is ignored today. A step must not behave that way.
- `--read-only` withholds the tool, as it does the other write tools.
- The path checks are the same as for the other write tools. `out` may not be `path`, and an
  existing `out` needs `overwrite`.

**Its text.** The description says what a step is. It lists the tools that can be steps, and says
that a batch cannot delete or reorder pages. It points to each tool's own resource page
(`klarpdf://docs/{tool}`) for that tool's arguments, rather than repeating them. It stays within
the 1,900-character limit that [M105](M105.md) set. The text goes in
`klarpdf/mcp_bridge/text/tools/edit.md`, in the layout [M179](M179.md) sets up.

**The reply.** It starts with what every write tool reports: `out`, `pages`, `bytes`, `source` and
`source_unchanged`. Then it gives each step's own reply, in order.

**Where else it is written down, in the PR that builds it.** A row in `PLAN.md`'s tool table
(§Architecture). A line in the Features list of `README.md`, and in
`klarpdf/mcp_bridge/README.md`. The tool's summary for Claude Desktop, which M179.3 moves into the
tool's file.

#### How it is tested

The bridge's tests are in `tests/test_mcp_*.py`.

- **One batch gives the same result as the same calls made one at a time.** Run the same edits both
  ways on the same document. Compare the text of each page, the marks, the field values, the outline
  and each page's rotation. Do not compare the bytes, because MuPDF writes a new `/ID` on every
  save. M100 tested several search terms in one call the same way. Leave one step out of the batch
  on purpose and watch the test fail.
- A failing step writes no file. Test it with the failing step first, in the middle and last.
- A batch keeps the tags and the encryption. A tagged file keeps its structure tree, and an
  encrypted file stays encrypted. Check the catalog, not the pages (CLAUDE.md, *`insert_pdf` copies
  pages, not documents*).
- A redaction step followed by other steps still passes the check on the final file. A redaction
  followed by `flatten` is checked on the flattened file.
- `delete_pages`, `reorder`, `merge`, `split`, `extract_pages` and `export_images` are refused as
  steps, and the error says why.
- `flatten` is refused anywhere but last.
- A misspelled key in a step is refused.

#### Open questions, for the session that builds it

These are settled with the owner in that session (CLAUDE.md, *Investigate a defect once*).

1. The tool's name.
2. How long the combined reply may get. `annotate` and the redactions can each return a long
   reply.
3. Whether the descriptions of the step tools mention the batch. Each mention costs characters in a
   description that may already be near its limit.

#### Order of building

Build in number order: M179, then M180, then M181. Nothing here needs a different order.

**M181 must come after M179.** M179 moves every tool's text into one Markdown file per tool. If
M181 came first, its text would go in the old place and M179 would have to move it.

**M181 does not need M180 first.** Number order puts it after M180 anyway. M180.1 pins the size of
the bridge's text, and M181 updates those sizes when it adds its tool. If M180.6 is built, it offers
the tools in groups, and the new tool goes in the group with the other write tools.

#### Rejected

- **A mode that keeps a document open between calls** (owner, 2026-11-23). The caller would open a
  document and get an id back, send edits against the id, and then save. Its one gain is that the
  caller could look at the result between steps. It was rejected for these reasons:
  - Almost every tool would change. Each write tool would need a second form that takes an id
    instead of `path` and `out`. Each read tool would also have to read the unsaved version, or the
    caller could not check its work, which is the reason to want the mode.
  - Work could disappear without warning. The unsaved document would live only in the server
    process. The edits would be lost if the client restarted the server, or if the conversation was
    shortened and the id was dropped. Every earlier reply would still have said the step worked.
  - A caller that forgot to save would lose everything.
  - The redaction check would have to wait until the save. So a reply saying that a redaction worked
    would promise less than it does today.
  - Claude can send several tool calls at once. Two edits to the same open document could arrive
    together, and their order would matter.
- **Steps that change the order of the pages**, `delete_pages` and `reorder` (owner, 2026-11-23).
  After one of them, a page number in a later step could mean the page's old place or its new one.
  A caller who also needs to delete or reorder pages makes that one call separately, before or
  after the batch. That leaves one in-between file, not one for each step.
- **Tools that read or write several files**: `merge`, `split`, `extract_pages` and
  `export_images` (owner, 2026-11-23). A batch has one input file and one output file.
