# M174

## Design

### M174 — lists that say what they hold (built 2026-11-11)

**Three parts, one PR each (owner, 2026-11-11).**

* **M174.1**, the engine: `klarpdf/model/` and `klarpdf/util/`. 134 findings.
* **M174.2**, the bridge: `klarpdf/mcp_bridge/`. 156 findings.
* **M174.3**, the app. 155 findings.

The engine goes first, because the bridge and the app both use the names it adds. Each part
switches mypy's `disallow_any_generics` on for its own files, in a `[[tool.mypy.overrides]]` block.
M174.3 moves it up to `[tool.mypy]` and deletes the block.

**The bridge's replies, for M174.2 (owner, 2026-11-11).** Every field of every reply is named, in a
`TypedDict`, and agents receive exactly what they receive today. That needs care, because the MCP
library reads each tool's return type to build the tool's reply schema, and checks every reply
against it. Measured on mcp 2.0.0:

* `server.py` writes its types as deferred text (`from __future__ import annotations`). Read that
  way, `-> dict` and `-> dict[str, Any]` give the same schema, `{"result": {"type": "object"}}`,
  and the same reply: the text, plus a second copy wrapped in `{"result": …}`. So
  `dict[str, Any]` on a tool changes nothing.
* A type the library cannot resolve, such as a `TypedDict` or a `Mapping` named in `server.py`,
  makes it drop the schema and the second copy. It says so only in a log line.
* A type it can resolve that names the fields would tell agents the fields, and a reply missing
  one would fail with an error.
* The inputs `marks`, `values`, `entries` and `regions` keep the same schemas when written as
  `list[dict[str, Any]]` and `dict[str, Any]`.

M174.2 compares the live server's tool list and replies before and after its change.
**Considered, not taken:** telling agents each reply's fields. It changes what every agent
receives, and a reply that drifted from its type would fail instead of arriving.

**Surfaces:** core, bridge and app. The types reach both consumers. The colour fix below changes
what the app shows and what a save writes, in the app and in the bridge, which reads our marks back
through `VirtualDocument` before any write.

**The names M174.1 adds.**

* `klarpdf/model/tuples.py`: `Box` (`x0, y0, x1, y1`), `Point`, `Color` (red, green, blue) and
  `Word` (one entry of `get_text("words")`).
* `PageEdit` in `page_edits.py`, for the type checker only, as `Mark` is: everything a page's
  `annotations` can hold, which is its marks and the records of another program's annotation moved
  or deleted. `PageRef.annotations` is `tuple[PageEdit, ...]`.
* `Char` and `Span` in `page_text.py`, for the entries of its index.
* `MarkPreset` and `WholePageStyle` in `content_marks.py`: the stamp presets and the watermark
  defaults, with their fields named.
* `SaveKeywords` in `edit_engine.py`: the keywords handed to `Document.save`.
* `TocEntry` in `toc_remap.py` (it existed, as a bare `list`) and `LinkDict` in `destinations.py`.

**Where `Any` is honest.** An outline row is `[level, title, page, dest]`, a list whose items have
different types. A link or a destination is a dict whose values change type with the key and the
kind of link. Both are PyMuPDF's, and PyMuPDF types neither. So their values are `Any`, under a
name that says what the data is. The bridge's replies are ours, which is why M174.2 names their
fields.

**What changes in code that runs.** Mostly types. These change a line of code:

* `add_annotation` and `replace_annotation`, and the undo commands and main-window methods that
  call them, take a `PageEdit` where they took `object`. They put it in a page's list, which is now
  typed. M172.2 chose `object` because there was no name for that list's contents.
* `_contiguous_runs` returns tuples instead of lists. Its one caller only unpacks them.
* The marks overlay paints a note's glyph for a highlight, underline or strikeout with a note. It
  tested `getattr(annot, "note", "")`. Only those three kinds have a note, so it now tests the kind.
* The overlay's hit test skips the two foreign-annotation records by name. They have no boxes, so it
  already skipped them. Naming them lets its return type say a hit is a mark.
* Two callers wrote a box as `tuple(box)`. One passes the box it already has. The other, in the
  bridge, builds it from four numbers.
* The mark dialog reads a stamp's default size from the stamp defaults. In that branch it already
  read those.

**What the types found: #398.** Once a mark's colour was typed as three numbers, `_stroke_color`
could not say so: it returned the colour as the file stores it. A PDF colour has one value (grey),
three (RGB) or four (printing ink, CMYK). A mark holds RGB only, and the viewer draws every colour
as red, green and blue. Reproduced in the real window on `main`:

* Adopting another program's grey mark raised `TypeError: QColor.fromRgbF(): not enough arguments`
  on every redraw, and the page's marks stopped drawing.
* A CMYK mark was drawn as red, green, blue and see-through, so it vanished.
* A saved file kept the colour as it came.

#398 was filed on 2026-09-25 and was still open. It also lists a line or pen mark with no colour,
which draws nothing and became red after an edit, with no warning.

**The fix (owner, 2026-11-11: keep the colour you see, and warn).**

* Every colour `parse_annotation` reads goes through `as_rgb` in `markup_palette.py`, which is
  M170's converter, now public. That covers text marks, pen strokes, lines, shape borders and fills,
  and a text box's fill. A grey `g` becomes `(g, g, g)`. MuPDF draws it as exactly that, rounded down
  to a whole level (measured: 0.5 is drawn as 127 of 255). CMYK becomes the RGB MuPDF draws it in,
  as M170 measured.
* A text box gives its text a colour in `/DA`, where ink is the `k` operator. The parser read `rg`
  and `g` only, so a CMYK text colour became black. It reads `k` now.
* The Adopt warning lists two new losses. "Its printing-ink colour (it will become the screen
  colour it is drawn in)". And, for a highlight, underline, strikeout, line or pen mark with no
  colour, "its lack of colour (it will become red)", or yellow for a highlight. PyMuPDF draws a
  highlight with no colour in black, and other programs may draw nothing, so the colour cannot be
  kept as seen. A grey loses nothing and is not listed. A shape with no border colour keeps having
  no border (M155), and is not listed either.
* `as_rgb` itself changed for grey. It used MuPDF's one-pixel conversion, which gives 0.502 for 0.5,
  one level away from the drawn page. It is now exact. No swatch name changes.

**Verified by breaking it** (M174.1).

* mypy failed on a bare `tuple` and `dict` planted in `klarpdf/model/`, and on one planted in
  `klarpdf/util/`.
* `is_listed` in the Annotations panel, changed back to `-> bool`, made mypy fail at both its uses.
  M173.2 found that this change made no error, because the marks list it filters was bare. That was
  the reason the owner gave for M174, and it now holds.
* The 18 new colour tests in `tests/test_foreign_adopt.py` fail with the colour passed through as
  the file gives it and the two warning lines taken out. The two in `tests/test_mcp_mark_colours.py`
  fail with the first of those.
* The full suite passes locally. It was run in full because the change reaches the engine.

**What M174.1 cost and what it caught.**

* **Cost.** 134 findings in 12 files, and 20 more errors the stricter types exposed where the bridge
  and the app call the engine. No suppression.
* **Caught.** #398, a defect a user could see, reported two months earlier. A check in the
  Annotations panel that did nothing until now. And the four places that took `object` for a page's
  marks, because there was no name for them.

**M174.2: the bridge (built 2026-11-11).** *Surfaces: bridge.* mypy now refuses a bare `tuple`,
`dict` or `list` in all of `klarpdf/`. 156 cleared, with no suppression. Agents receive exactly the
replies they received before, measured below. Three answers to malformed input change.

**What it adds.**

* `klarpdf/mcp_bridge/replies.py` names every field of every reply, as `TypedDict`s: 23 tools, and
  the entries their lists hold. A field sent only sometimes is `NotRequired`. It is imported for
  type checking only.
* **The redaction reply is the exception.** It is put together from parts (`_merged`): the write,
  its verification, the residual scans, the image report and what the call adds. So one type,
  `RedactionReport`, names every field any part holds, and all are optional. What it checks is that
  no part writes a field that is not there, or of the wrong type. `_merged` itself is written with
  `update`, which mypy can follow, and keeps the same key order and the joined warnings.
* **The tools keep `-> dict[str, Any]`** and hand their reply over through `server._sent`, a
  `cast` and nothing more. This is the decision of 2026-11-11 above: the MCP library builds the
  reply schema from the tool's own type, and a `TypedDict` there would drop the schema and the
  structured copy of every reply.
* **What an agent sends is `object` until the code checks it.** `marks`, `regions`, `entries` and
  `values` are `list[dict[str, object]]` and `dict[str, object]`, which give the same input schemas
  as before. `resolve_pages` and `set_outline_override` already checked each value, and now say so
  in their types.
* Internal names: `_Table`, `_Unread` and `_TableFound` in `tables.py`, which keep the keys that
  start with `_` out of a reply; `_Expectation`, `_QueryStats` and `_Partial` in `redaction.py`;
  `_OutlineIn` in `transforms.py`; `_StyleKey` in `headings.py`.
* `tests/test_no_dead_code.py` skips the fields of a `TypedDict`. Code reads a field by its key,
  as a string, and vulture matches names only, so it reported all 80 as unused variables. A
  `TypedDict` class nothing uses is still reported, because that finding is on the class.

**What typing the agent's input found.** Three answers to malformed input. In each, nothing wrong
was written, except the second, where a box nobody meant was redacted.

* **`set_outline` with `page: "3"`** answered with Python's own *unsupported operand type(s) for -:
  'str' and 'int'*. `_tops_outside_their_page` subtracted from the page before anything checked it.
  It now skips a page that is not a whole number, and `set_outline_override` refuses it with its
  own reason: *page must be an integer*.
* **`redact_regions` with `box: "1234"`** read the string as four numbers, one per character, and
  redacted the box `(1, 2, 3, 4)`. `annotate` did the same. `box: 5` and `box: ["a", 1, 2, 3]` got
  Python's own errors from `redact_regions`.
* **`boxes: "ab"`** was read as two boxes, one per character.

Both tools now read a box through one function, `queries.parse_box`. It takes a list of four
numbers and nothing else, and refuses with the message `annotate` already gave: *box must be four
numbers*. `boxes` that is not a list is refused as such.

**Two more changes in code that runs**, each with no change in what it does: `_recode_report` used
`now` for an image's new encoding and then for the total of new sizes, and the totals are renamed;
`_banner_title` reads the banner once and returns early if there is none, which its one caller
already checks.

**Verified by breaking it, and by comparison** (M174.2).

* **The replies, over the corpus.** A script called every tool on the 114 corpus documents under
  8 MB: the reads over pages 1-3, and the writes on 11 of them, with one `annotate` call that
  sends a wrong mark type. It stored a hash of each reply, never its text, because the corpus holds private
  documents. Before and after: the tool list (descriptions, input schemas, reply schemas) is
  identical, and 1,407 of 1,408 replies are identical. The one that differs, a `delete_pages`
  reply, also differed between two runs of the unchanged code.
* mypy failed on a bare `list` and `dict` planted in `klarpdf/mcp_bridge/`, and on a reply with a
  misspelt field (`Extra key "has_text_layr" for TypedDict "InfoReply"`).
* The new tests for malformed input fail on the old code, except two: `annotate` already refused a
  box of `5` and one holding a word.
* The dead-code test's skip, turned off, fails both its planted check and the real scan. The
  planted check shows what it still reports: an unused `TypedDict` class, an unused class attribute
  and an unused variable.
* The bridge's tests and the project's rule tests pass locally. The full suite was not run
  locally: the change reaches no code in `klarpdf/model/`, `klarpdf/util/` or the app.

**What M174.2 cost and what it caught.**

* **Cost.** 156 findings in 7 files. One new module of types, and a rewrite of three helpers so
  mypy can follow them (`_result`, `_merged`, `_public`). One skip in the dead-code test. No
  suppression.
* **Caught.** No defect in any reply. Three answers to malformed input, one of which redacted a box
  nobody asked for. And a name used for two things.

**M174.3: the app (built 2026-11-11).** *Surfaces: app.* `disallow_any_generics` moves up to
`[tool.mypy]`, and the override block is deleted. mypy now refuses a bare `tuple`, `dict` or `list`
in everything it checks. 155 cleared, with no suppression. Both platforms reported the same 155.

**What it adds.**

* In `viewer/pdf_view.py`: `_StoreKey`, the key of a page's picture in the store (the page, the
  device scale and the extra spin); `_Piece`, a piece of a page's picture in tiles; and `_Page`, one
  page in the scene, as a `TypedDict`: its two items, where it is, its spin, and the item that shows
  a carried picture.
* The store's handle says what its keys are. The page view holds an `Owner[_StoreKey]`. The class
  was `_Owner`, and is public now that the page view names it. The store itself takes any key, so the
  one method that hands keys back says which kind they are, with a `cast`.
* `_ChromeState` in `main_window.py`: what full screen and the slideshow put back. `SignatureSettings`
  in `store/settings.py`: how a signature image was last placed. `_StampStyle` in
  `ui/mark_dialog.py`. `PageClip` in `app.py`: one copied page. `_RowKey` in
  `organize/thumbnail_panel.py`: which page a thumbnail row shows.
* **What the settings file holds is `object` until the code checks it**, as with what an agent sends
  (M174.2). The file is the app's own, but a person can edit it by hand.

**What the types found: a remembered page that is not a whole number.** The settings file keeps the
page each document was last read at. `PdfView.open_at` passed it to `int()` unchecked. A page of
`"abc"`, `null`, a list or an object raised in the window's first show. Reproduced on the old code by
launching the app as a double-click does, on a PDF whose remembered page was `"abc"`: the call that
opens the document raised `ValueError`, before the event loop started, and the process exited with
status 1. So the app did not start. The app writes a whole number there, so this needs a hand edit or
a damaged file. Anything but a whole number now opens page 1, and the same launch opens the window.
A new test covers the four values, and fails on the old code with all four.

**Four places relied on something nothing stated.** None was wrong yet. Each now says it.

* **The marks overlay kept the marks being dragged and their outlines in one list.** A drag of
  another program's annotation put that annotation in the list too. The step that ends a drag of our
  own marks read the marks from the list, and never met another program's only because that drag
  ends in a different method. The marks now have their own list (`_move_marks`), and the outlines
  theirs.
* **The page view's next-piece helper returned no piece when asked not to grow one.** The drawing
  loop relied on never asking. It is two methods now: `_next_seed`, where the next piece starts, and
  `_next_piece`, which grows it.
* **The text-box editor read its fixed width when a flag said the box had one.** The width is set
  exactly then, so the editor now tests the width itself.
* **`_Wip.origin` was declared as two decimal numbers.** It holds whole pixels, from PyMuPDF's
  `IRect`, and `QImage.copy` takes whole numbers. It now says so.

**And one helper that returned `Any`.** The link navigator's hit test served internal links, kept as
`(box, page, top)`, and web links, kept as `(box, URI)`, so it could not say what it returned. Each
entry is now a box and what it points to.

**What changes in code that runs.** The fix above, the restructuring in the four places, and the
link entries. Two copies made with `tuple(...)` are dropped, because the value is already a tuple:
the note popup's anchor and its toggle key. A line bar is built from its four numbers instead of
`tuple(bar)`. A stamp placed from the Recent Signatures menu is built in two branches, with and
without remembered settings, because mypy cannot pass `**` an empty dict or the settings.

**Verified by breaking it** (M174.3).

* mypy failed on a bare `tuple` planted in `viewer/` and a bare `dict` planted in `main_window.py`.
  With the setting back in the override block for `klarpdf/` only, the same plants passed.
* The new test fails on the old code with all four values.
* The full suite passes locally. It was run in full because the change reaches the page view and
  the main window, which most tests go through.

**What M174.3 cost and what it caught.**

* **Cost.** 155 findings in 22 files, and 16 more errors at 6 places where a known type showed what
  the code assumed. No suppression.
* **Caught.** A damaged settings file stopping the app from starting. Four places that relied on
  something nothing stated. And a helper whose two kinds of entry could not share a type.

**What M174 cost and what it caught, all three parts.** 445 findings, no suppression. Two defects a
user could see: #398's grey and printing-ink marks, and the damaged settings file. Three bad answers
to malformed agent input, one of which redacted a box nobody asked for.
