# M165

## Design

### M165 — a drag survives what the page does around it *(unplanned)* (2026-11-06)

[#431](https://github.com/utyagi24/klarpdf/issues/431). Working on a form, the owner dragged a text
box's width handle and nothing happened. The console the launcher ran in filled with `Internal C++
object (PySide6.QtWidgets.QGraphicsRectItem) already deleted`, once per mouse move.

**Surfaces: app only.** `viewer/` is outside the wheel and the bridge has no drags, so there is no
bridge test to write.

#### Cause

Two facts meet. A drag keeps an item in the scene: the outline of a move or resize, the band of a
marquee, redaction or crop, the preview of a shape or pen. And `_build_scene` calls `scene.clear()`,
which destroys every item, and then repaints overlays that know nothing about drags. So any rebuild
during a drag left that drag holding a dead object, and each mouse event after it raised.

The owner's rebuild came from the text box editor. `_on_editor_focus_out` commits one tick after the
editor loses focus, on purpose: focus reaches a formatting-bar menu before that menu's `aboutToShow`
(M27). Qt moves focus before it delivers a press, so the order was: the focus-out queues the commit,
the press starts the drag, the commit runs, and its undo push reloads the view.

Measured with real mouse events, which gave the owner's log line for line:

* The outline was alive after the press and dead as soon as the event loop ran. Each move then raised
  in `update_resize`, and the release in `_drop_resize_ghost`.
* That release raised before `_resize_handle` was cleared, so the view still read as resizing. The
  next click's release finished the old resize, against a box the edit had already replaced. That
  pushed a "Resize text box" step that changed nothing, and its reload destroyed the outline of the
  move the same click had started. A click on empty page then raised in `finish_move`.
* The document was not damaged. The text edit was kept, and the resize was lost.

**Neither M163 nor M164 caused it.** `508918d`, from before both, fails the same way, and there a
re-open that changed nothing failed too, because the old commit compared the auto-grown rect. M164's
stricter check narrowed it.

A zoom or a reload mid-drag did the same to every drag: move, resize, marquee, shape, pen, redaction
and crop. So fixing only the editor's order would have left the class.

No test saw it because the tests called `_commit_textbox` or `view.mousePressEvent` directly, and a
direct call skips the focus change that the whole defect depends on.

#### The fix

The two parts do different jobs, and both are needed.

**A press commits first.** `PdfView.mousePressEvent` calls `commit_before_press` before it acts on a
press, so the press sees the page as it now stands, and the reader's drag works. The delayed commit
stays for the format bar, and otherwise finds the editor already gone. The commit's rebuild clears the
selection, so it is put back, with the edited box swapped for what replaced it. Without that, the
handle the reader aimed at would vanish from under the press. The handle is read before the commit,
because a shorter text pulls an auto-width box's right edge in. The press is then no longer on the
handle, but a text box's width follows the cursor, so the drag still does what was meant.

**A rebuild ends every drag.** `_build_scene` calls `_end_drags` before `scene.clear()`, while the
items are still alive. Nothing is applied, and an armed tool stays armed, as it does after a press
off the page. A drag's own commit is not caught by this, because each `finish_` lets go of its items
before it commits.

**Rejected:**

* **Remove the delay.** It is what stops a commit when the reader is only reaching for the format bar.
* **Let the press only close the editor.** Simple, but the owner's drag would still do nothing, and
  clicking another box while editing would take a second click.
* **Carry the drag across the rebuild.** A zoom moves the scene points a marquee, redaction or crop
  band holds, and an edit can replace the mark a drag holds.
* **Check the item in every `update_` and `finish_`.** It stops the error in each place and leaves
  the stale drag running.

**Not changed:** the `CLAUDE.md` rule against rebuilding inside a Qt callback stands.
`commit_before_press` rebuilds inside `mousePressEvent`, but before Qt's own handler runs, so nothing
is walking the items, and every drag's release already commits the same way. After a rebuild ends a
drag from the combined Redact slot, the slot stays on its region form until the next drag.

#### Checks

`tests/test_drag_rebuild.py` sends real mouse events through the application, so the editor loses
focus before the press, as it does live. It covers the owner's drag, a fixed-width box, a press on
another box, a press with another mark selected, a box emptied by the edit, and an edit that changed
nothing. Every drag, a foreign move included, is then rebuilt under by a zoom and by a reload. Each
one must end, apply nothing and leave Undo empty. A text selection holds no item across a drag, so it
needs nothing ended, and a test pins that. **Broken on purpose 14 ways:** each part of the fix in turn,
and every kind of drag left out of `cancel_drags` one at a time. Each break failed its own tests. A
first pass found two gaps: `scene.clear()` hid a `cancel_drags` that left its items in the scene, and
a foreign move was not tested at all. A stale one would have applied a cancelled drag on release.

**A hand check on Windows, done by the owner on 2026-11-06.** Double-click a text box, change its text, then drag its right-edge
handle without clicking anywhere else. The box should resize, the text should stay changed, Undo
should take back one thing at a time, and the console should stay quiet. Then start a drag on any
mark and zoom with Ctrl+wheel before letting go: the drag ends and the mark stays where it was.
