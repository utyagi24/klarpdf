# M180

## Design

### M180 — the bridge takes less room in sessions that do not use it (planned 2026-11-17)

The owner asked on 2026-11-17: in a Claude session that never works on a PDF, how much of the
context does the bridge take? This plan records the answer and the changes that would make it
smaller.

**Surfaces: bridge only.** Every change is in `klarpdf/mcp_bridge/` and its install guides. Nothing
in `klarpdf/model/` or `klarpdf/util/` changes, so the app is not reached.

#### What a session pays today

Clients load a server's tools in one of two ways.

- **Claude Code loads the tool names only.** It lists each tool's name when a session starts. It
  loads a tool's full definition, its description and its parameters, only when it is about to
  call that tool. This is called deferred loading.
- **Some clients load every tool's full definition when a session starts.** Which clients do this
  has not been checked. M180.1 checks it.

Every client puts the server's instructions in the context in full, in every session.

The MCP project's guide for clients says when to load tools on demand: [Client Best
Practices](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/docs/2026-07-28/develop/clients/client-best-practices.mdx),
protocol revision 2026-07-28, §Progressive Tool Discovery. It calls this progressive discovery. It
tells clients to load every definition while the definitions are a small share of the context
window, and suggests switching at 1% to 5% of the window. The bridge's full definitions, about
12,000 tokens, are about 6% of a 200,000-token window and about 1.2% of a 1,000,000-token one. So
a client that follows the guide may load them in full. The size of the full definitions matters
even in clients that can load tools on demand.

#### The parts

One PR per part. Build in number order. M180.1 comes first because the later parts lower the
limits it adds.

Build M180 after M179, which moves the bridge's text into Markdown files, one per tool
(`docs/milestones/M179.md`). Every text change below is then made in those files. This milestone
was numbered M178 until 2026-11-23, when the owner asked that the numbers follow the order of
building.

**M180.1 — measure what each client loads, and pin the sizes.**

- Check which clients load every tool's full definition when a session starts: Claude Code, Claude
  Desktop, Codex and Gemini CLI. Check also whether any of them shows the reply schemas to the
  model. Check whether any of them starts a server only when a task needs it, as the guide's
  §Dynamic Server Management describes. Record how each one was checked. Claude Desktop may need
  the owner to check it by hand.
- Replace the token estimates with one exact count. In Claude Code, `/context` shows the tokens
  each MCP server takes. The owner runs it.
- Add two size limits to `tests/test_mcp_docs.py`. One is for what every session pays: the
  instructions and the tool names. The other is for the full definitions. Each limit starts at
  today's size. Later parts lower them. Raising one needs the owner's go-ahead, as raising the
  1,900 limit does. Like the existing tests there, they read the live server, so a new tool is
  counted the day it is added.
- Break each limit on purpose, by adding text to one description, and watch the test fail.

**M180.2 — move "what survives a write" out of the instructions.**

The paragraph is 716 characters, 39% of the instructions. It moves into the descriptions of the
tools it is about.

- The five tools that move pages (`reorder`, `delete_pages`, `extract_pages`, `split` and `merge`)
  each get one sentence. It says that the structure tree, `/Perms`, the `/Names` tree and the
  encryption do not survive, and that Claude should tell the user if the file had them. Today
  `reorder`'s description says what survives the move, and not what is lost.
- The five tools that keep every page in place (`fill_form`, `flatten`, `set_outline`,
  `redact_text` and `redact_regions`) say that everything survives, where they do not say it
  already.
- The instructions go from 1,839 characters to 1,121. What Claude Code loads in every session goes
  from 2,423 characters to about 1,705, 30% less.
- In a client that loads every tool, the total grows a little. Five sentences of about 170
  characters add about 850, and 718 come out of the instructions.
- Claude now sees the warning when it loads the tool, just before it calls it. That is when it
  matters.
- The `--read-only` build does not change. It already leaves out the write paragraphs (M176).
- Lower the limit for what every session pays (M180.1) to the new size.

**M180.3 — remove the titles from the parameter lists, and decide on "or nothing".**

About 2,800 characters, 27% of all parameter text, about 700 tokens in a client that loads every
tool. In Claude Code this changes nothing at the start of a session, but each tool Claude loads
gets shorter.

- Remove the `title` keyword from each parameter list after the tools are registered, in
  `create_server`. It cannot be done in `guarded`, because the library builds the parameter list
  after `guarded` returns. Remove only the keyword. A parameter called `title`, if one is ever
  added, must stay.
- The check that refuses a misspelt argument name (M106) reads only the parameter names
  (`server.py`, where `StrictArguments` is fed). The titles do not reach it.
- A test reads the live server and fails if any parameter list still holds a `title`. Break it on
  purpose: skip the removal for one tool.
- Check by hand that Claude Code, Codex and Gemini CLI still call the tools correctly. Nothing in
  the test suite covers the client side.
- **For the build session to decide:** whether to write an optional parameter as a plain value
  instead of "a value, or nothing" (1,147 characters). Clients may send `null` today. The build
  session checks what a call with `null` and a call without the parameter do before and after.
  If they become a plain value, change their type words in each tool file's `# Parameters` part
  too (M179.4). Its test fails until they match.
- Lower the limit for the full definitions (M180.1) to the new size.

**M180.4 — shorter descriptions.**

Descriptions are 72% of the full definitions. M105's rule already says what goes where. What Claude
must know before it calls a tool stays in the description. What it needs only to read the reply
moves to `klarpdf://docs/{tool}`, which after M179 is the `# Reference` part of the tool's file. An
explanation of one parameter can move to that parameter's line in the `# Parameters` part (M179.4).

- Go through the descriptions, longest first, and move out what is about reading the reply. For
  example, `get_tables` has a paragraph on the reply fields `header`, `title`, `continues_from` and
  `continuation_checked`.
- A second place for guidance about a reply is the reply itself, as a note that appears only when
  it applies. It costs nothing until then. `get_tables` already does this: each region it could
  not read says what to try. For example, `get_links` tells Claude never to say "these are all the
  links" when the reply has more. The reply that has more could say that instead.
- Make each description's first sentence say what the tool does, in the words a user would use.
  A client that searches for tools shows a name and a one-line description first, and matches the
  search against them (the guide's "catalog" step). Three first sentences today are mostly the
  names of reply fields: `get_outline`, `get_tables` and `get_heading_candidates`.
- What stays: anything that would lead to a wrong action or a wrong claim if Claude had not read
  it before the call. That includes everything on redaction and on writing files.
- The 1,900 limit stays. It protects against the client cutting a description off. It is not a
  size to fill. The rule *A tool description is a budget, not a place* in `PLAN.md` §Architecture,
  and the CLAUDE.md gotcha on MCP descriptions, get one sentence saying so.
- This part has 23 descriptions to go through. It may be built in more than one PR, for example
  the reading tools, then the write tools, then redaction.
- Check each changed tool through Claude Code on one real document. A shorter description can make
  Claude call a tool wrongly, and the test suite cannot see that.
- Lower the limit for the full definitions (M180.1) to the new size.

**M180.5 — say in the install guides what the server costs, and how to avoid it.**

`klarpdf/mcp_bridge/QUICKSTART.md`, `klarpdf/mcp_bridge/README.md` and `README.md` tell users to
add the server with `--scope user`, so that it is there in every folder. QUICKSTART gives the
reason: the server works on any PDF anywhere. So every session in every folder pays what M180.1
measures.

- Add what it costs, with the number from M180.1.
- Add the ways to pay nothing where PDFs are not used: add the server for one folder only
  (`--scope local` or `--scope project`), turn it off for one session with `/mcp`, or start it with
  `--read-only` to pay less.
- Whether `--scope user` stays the recommendation is a question for the owner (below).

**M180.6 — choose which groups of tools the server offers.** *Only if M180.1 finds that a client the
owner uses loads every tool when a session starts.*

- `--read-only` already halves the full definitions. A switch could offer chosen groups instead,
  for example reading, page changes, forms, annotations and redaction.
- In Claude Code it saves about 8 tokens for each tool left out. That is not worth a new switch for
  Claude Code alone.
- The switch is read once, when the server starts, as `--read-only` is. It never changes the tool
  list during a session (see *Rejected*).

#### Rejected

**Merging less-used tools into one tool** (the owner's question, 2026-11-17).

- The less-used tools are already the smallest. The six page tools (`reorder`, `delete_pages`,
  `rotate`, `split`, `extract_pages` and `merge`) are the six shortest definitions, 4,576
  characters together.
- In Claude Code, merging them saves five names, about 40 tokens of the 650.
- In a client that loads every tool, the most it can save is the parameters the six repeat, about
  1,300 characters, plus a little structure. That is under 4% of the total. M180.3 saves about
  twice as much and changes no tool.
- It costs more than it saves:
  - In Claude Code, using one of the six operations would load the description of all six.
  - Claude Code asks permission per tool. Today a user can let `rotate` run without asking while
    `delete_pages` still asks. A merged tool puts both behind one permission.
  - One tool would carry the parameters of all six operations, and most apply to only one of them.
    Claude would have to work out which parameters go together, so more calls would go wrong.
- Merging is right in one case: two tools that are always called one after the other for one
  task. One tool for the whole task saves a call and a reply. That saves reply text, not
  definition text. No such pair is known in the bridge.

**One tool that describes the others when asked.** This is the same idea taken to its end: a single
`klarpdf` tool whose reply lists the operations. Claude Code already does this for every server, by
loading a definition only when it is needed. In other clients it would lose the per-tool
permissions, and Claude would see an operation's parameters only after a first call.

**A lower limit for each description.** It would cut by a number, not by what Claude needs. M180.4
moves text by kind instead, as M105's rule says, and the limits from M180.1 record the result.

**Removing the reply schemas to save space.** They are 3,661 characters. The guide asks servers to
provide them. A client that lets Claude write code to call the tools builds typed functions from
them (§Programmatic Tool Calling). A client that loads tools on demand shows them when Claude
looks at a tool before calling it. M180.1 still checks which clients show them, so their cost is
known.

**Changing the tool list during a session**, for example a tool that turns on a group of tools
when Claude asks for it. The client would have to list the tools again. The guide warns that
adding or removing tools in the middle of a conversation throws away the prompt cache (§Interaction
with Prompt Caching). The prompt cache is the AI provider's stored copy of the start of the
conversation, which makes each later turn cheaper. The bridge's tool list never changes while it
runs, and it stays that way.
