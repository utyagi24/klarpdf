# M182–M185

## Design

### M182–M185 — OCR, and correcting what it reads (planned 2026-11-24)

The owner asked on 2026-11-24 whether agents such as Claude Code and Codex have OCR built in, and
whether the app and the bridge should add it. OCR is software that finds the words in a picture of
a page and writes them into the PDF as hidden text. That hidden text is what lets a reader search,
select and copy words on a scanned page.

Agents have no OCR. Their models can read a picture of a page, and the bridge's `render_page`
already gives them one. But that puts no text in the file. On a scan with no text:

- a person in the app cannot search the page, or select and copy a sentence;
- the bridge's `search`, `extract_text`, `get_tables` and `redact_text` find nothing.

OCR is never fully right, so this plan pairs it with correction: by a person in the app, and by an
agent through the bridge.

This reverses the July 2026 rejection in `PLAN.md` §Future enhancements. Its reason was that OCR
"needs a bundled Tesseract". PyMuPDF 1.27.2.3, which we ship, has Tesseract's engine built in
(`Page.get_textpage_ocr`, `Pixmap.pdfocr_tobytes`). It needs only a language file. Our copy
reports the engine as "tesseract 5.0.0-alpha".

**Surfaces.** M182 and M183 add to the core (`klarpdf/model/`) and the bridge. M184 and M185 are
the app, built on M182's and M183's core functions. A core function wants a test on both sides,
so the app's tests of M182's and M183's functions come with M184 and M185.

#### What was measured (2026-11-24)

Measured with the three English files from the Tesseract project, on 168 pages from 91 test
documents that have text. Each page was drawn as a picture and read with OCR. The answer key was
the words the page's text layer draws visibly: spans with fill or stroke and alpha above 0, the
same test as `get_heading_candidates`. The pictures were drawn from the file, so they are cleaner
than any real scan.

| How the page was read | Words exact | Words found anywhere | Median time a page |
|---|---|---|---|
| 300 dpi, fast file (4.1 MB) | 91.7% | 91.9% | 3.7 s |
| 300 dpi, standard file (23.5 MB) | 91.7% | 91.9% | 8.5 s |
| 300 dpi, best file (15.4 MB) | 91.7% | 92.0% | 19.3 s |
| 150 dpi, standard file | 88.6% | 88.9% | 6.7 s |
| 72 dpi, standard file (PyMuPDF's default) | 17.5% | 18.6% | 2.5 s |
| Simulated poor scan, standard file | — | 89.5% | 7.6 s |

- The times were taken with seven pages read at once on 8 cores.
- "Words exact" matches each answer-key word with the OCR word over it, by position. "Words found
  anywhere" ignores position. The poor scan is tilted, so only the second applies.
- The simulated poor scan was drawn at 200 dpi, in grey, tilted 1.5°, and saved as a JPEG at
  quality 25.
- 100 of the 168 pages had 95% or more of their words exact at 300 dpi.
- Text under 7 pt: 88% exact at 300 dpi, 74% at 150 dpi.
- An OCR word sat over 97.5% of the answer key's words, and 94% of those were spelled right. A box
  of junk over a word also counts here, so this overstates how well OCR finds words.

**The one real scan in the corpus**, checked by eye on its top block, against the other program's
OCR text the file already carries. The standard file read the customer number, the town and all
three phone numbers correctly. The file's own OCR got the customer number, the town and two of
the phone numbers wrong. Both garbled the vehicle number, and both skipped the shaded header
cells.

**Failures seen on the eight worst pages:**

- **A page shown sideways reads as junk.** Its text runs up and down the screen instead of left to
  right. The page measured has a quarter-turn rotation set (`/Rotate 90`). With the rotation
  undone, the same page read 434 words correctly. A page scanned sideways looks the same, but has
  no rotation setting to undo. Nothing in the engine detects which way up a page is.
- **A table with coloured rows gave 13 of 331 words.** The grey poor-scan version of the same
  page gave 253.
- **Shaded table cells came out as junk, and shaded headers were skipped.**
- **Photos and charts produce junk words.** A searchable copy would carry them.

Two low scores were the answer key's fault, not the OCR's: titles stored one letter at a time
("O P T I M U S"), and a text layer whose letters are out of order. OCR read both correctly.

**Gotchas found:**

- PyMuPDF's OCR reads at 72 dpi unless told otherwise. Pass 300.
- `Pixmap.pdfocr_tobytes` returns no words, and no error, for a grey picture. The same picture
  converted to RGB reads normally. `Page.get_textpage_ocr` draws an RGB picture, so it is not
  affected.
- PyMuPDF cannot open HEIC photos, the iPhone's format. The app already turns PNG, JPG, GIF, BMP
  and TIFF images into pages (M35, `IMAGE_EXTENSIONS` in `klarpdf/model/virtual_document.py`).

**Redaction already acts on hidden OCR text.** On a scan that carries another program's OCR text,
`redact_text` finds a word in that hidden text and removes the picture under its box (measured on
a scan in the owner's OCR folder). The reply does not say that the matched text was hidden. The
check after the redaction reads the same hidden text, so a word the OCR misread is missed by both.

#### Decisions (owner, 2026-11-24)

1. **English only at first.** Other languages later, when asked for.
2. **Which English file ships is not decided yet.** The three files scored the same on clean
   pictures, and the owner wants a wider test on real scans. Until then, the app and the bridge
   let the person choose among the files in a folder they name. The chosen file is then packaged
   in both the installer and the bridge's package. That step gets its number when it is planned.
3. **OCR runs only when a person or an agent asks for it on a document.** Nothing runs OCR on its
   own. Redaction never runs OCR. It acts only on text the document already has, so a person turns
   on text detection first.
4. **The four steps below, built in number order.**

#### M182 — read a scan's words (core and bridge)

- **Core.** A function in `klarpdf/model/` that reads one page with OCR and returns its words. Each
  word has a number, its text and its box, in the unrotated page coordinates the rest of the core
  uses. It always reads at 300 dpi, from an RGB picture.
- **Choosing the file.** The function takes the language file to use. The bridge finds the files
  in a folder the person names. Each call can say which file to use. The tool's reply says which
  file it used and how long each page took.
- **Bridge.** A read-only tool that returns the words for the pages asked for, and writes no file.
  It skips pages that already have visible text, unless asked.
- **Tests.** Build an image-only page from a page with known words, inside the test, and check
  the words and their boxes. CI needs a language file for this. How CI gets it is decided when
  M182 is built: committed to the repo, or downloaded and checked against a pinned checksum.
- **Sideways pages.** M182 decides whether to detect them or to report them so the caller turns
  the page first.
- **Order with M179.** M179 moves each bridge tool's text into its own file. If M179 is built
  first, the new tool's text starts in that layout. If not, M179 moves it with the rest.

#### M183 — make a searchable copy, with corrections (core and bridge)

- **Core.** Write words as hidden text to a copy, each word placed in its box and stretched to its
  width. No page moves, so the copy keeps everything the document holds, as `fill_form` does.
  Write our text apart from the page's own drawing, marked as KlarPDF's, so a later run can
  replace it without editing the page's own content. Check that this works when it is built.
- **Bridge.** A tool that writes a new file. It either runs OCR itself, or takes words from the
  caller: corrected text by word number, and new words with boxes for words the OCR missed.
- **How an agent corrects a page:** read the words with M182's tool, look at the page with
  `render_page`, send the corrections, get a new file.
- **To decide when built:**
  - what happens to hidden text another program already wrote: replace it, or keep it;
  - what `redact_text`'s reply says when the words it matched are hidden text;
  - how the file records that KlarPDF added the text, and which words were corrected.

#### M184 — "Make Searchable" in the app

- A menu command that reads, with OCR, the pages of the open document that have no visible text.
  It shows progress and has a cancel button. It runs away from the window's own thread, so the
  window stays responsive.
- The result is an unsaved change, like any other edit, and is saved through the usual save path.
- A setting chooses the language file, while the file is not decided.
- Afterwards, search, select and copy work on those pages.
- To decide when built: whether the app should open an image file directly as a document, rather
  than only add it as a page.

#### M185 — correct words in the app

- A mode that shows the OCR words over the page. Click a word to retype it. Draw a box to add a
  word the OCR missed. Delete junk words, such as those read from a photo.
- It saves through M183's core function.

#### Choosing the file

The owner's real scans live in a private folder outside the repo. Their names never go into git.
Once a page is corrected, with M183 or M185, it becomes an answer key, and the three files can be
scored against it. The file is chosen then.

#### Not in this plan

- **Running OCR on its own**, when a document opens or during redaction (owner, 2026-11-24).
- **Other languages**, until someone asks.
- **HEIC photos.** Opening them needs a new dependency.
- **Cleaning the picture before OCR**, such as straightening a tilted page or removing specks.
  Revisit if the real scans need it.
