# M186

## Design

### M186 — files as tabs in one window (planned 2026-11-25)

The owner asked on 2026-11-24 to explore tabs, so that several files can be open in one window.
Today each file opens in its own window.

**Surfaces: app only.** Nothing in `klarpdf/model/` or `klarpdf/util/` changes, so the MCP bridge
is not reached. Nothing moves into the core.

#### What the reader sees when it is done

- Each window holds one or more files, one tab per file.
- The tabs sit in the window's top strip, where the title bar shows `report.pdf — KlarPDF` today.
  So they take no extra space. The minimise, maximise and close buttons stay on the right.
- The row of tabs shows even when the window has only one file.
- Each tab holds a whole window as it is today: its own menus, toolbars, sidebar and pages. Below
  the tabs, the reader sees the menus and toolbars of the tab in front.
- Double-clicking a PDF in File Explorer while KlarPDF is open opens it as a new tab in the front
  window. File ▸ Open and Open Recent open a new tab in their own window.
- Opening a file that is already open brings its window to the front and its tab forward. It never
  opens a second copy.
- Dragging a tab out of the row gives that file its own window. Dragging a tab onto another
  KlarPDF window adds it to that window's tabs.
- To move pages between two files, the reader puts their windows side by side and drags page
  thumbnails across, as today. The same two windows serve to compare the files.

#### Decisions (owner)

1. **Tabs, not a faster way to switch windows** (2026-11-25).
2. **Each tab holds a whole window, with its own menus and toolbars** (2026-11-25). The owner first
   chose one menu bar and one toolbar per window, with the tabs below them. The owner changed this
   after the comparison under *Options not chosen*.
3. **A double-click in File Explorer opens a new tab in the front window** (2026-11-25).
4. **Tabs can be pulled out into their own window and put back** (2026-11-25). This is for moving
   pages between files, and for comparing files side by side.
5. **The row of tabs shows even with one file, in place of the file name in the title bar, so it
   takes no extra space** (2026-11-25). This sets aside the owner rule that controls which do not
   apply are hidden (M45, M77), because a tab in the title bar costs no space.

#### What was measured (2026-11-24 and 2026-11-25)

Both measurements ran on WSL with no screen (`QT_QPA_PLATFORM=offscreen`), on `main` at `2946ae7`.
Neither has been repeated on Windows.

- **Shortcuts.** Two whole windows were put in one tabbed window, each with a Save command on
  Ctrl+S. Only the tab in front answered Ctrl+S. The hidden tab did nothing. Alt-key menu shortcuts
  and keyboard focus were not checked.
- **What one whole window costs**, built ten times on a 20-page file, median:
  - 26 ms to build. The menus and toolbars (`_build_actions`) took 13 ms of that.
  - 134 controls (Qt widgets: buttons, menus, panels). 101 of them are the menu bar and the two
    toolbars.
  - 150 commands (Qt actions: one per menu item or toolbar button).
  - 10.6 MB of memory before it was shown, the file included. How much of that is the menus and
    toolbars was not measured.

So the cost of every file carrying its own menus and toolbars is small, even with 20 files open.

#### How it is built

Four parts, one PR each, built in order. Each part is checked by hand on Windows before the next
starts.

##### M186.1 — an outer window, with nothing changed on screen

A new outer window holds today's `MainWindow` as a child. In this part it always holds exactly one,
so nothing on screen changes.

The parts of `MainWindow` that act on the whole window move to the outer window. They are:

| What | Where it is today |
|---|---|
| The smallest size the window allows (#358) | `main_window.py:237`, `resizeEvent` at `:3295` |
| The title, and its unsaved mark | `:362`, `:2924`, and `setWindowModified` at `:1622` |
| Size and place on opening | `_place_window` at `:3275` |
| Freeing page pictures when the window loses focus or is minimised (M87.2) | `changeEvent` at `:1138` |
| Checking for changes by another program when the window comes back to the front (M24) | `changeEvent` at `:1150`, and `:3198` |
| Full screen and slideshow (M78) | `_enter_chromeless` at `:1440`, `_exit_chromeless` at `:1471` |
| Asking to save on close | `closeEvent` at `:3340` |

In `app.py`, `PdfApp.open_document` builds the outer window around each new file.
`platform_integration.activate_window` must be given the outer window, because that is the window
Windows brings to the front.

**Tests.** `open_document` keeps returning the file's window. So the tests that reach into its parts
(`w.view`, `w.vdoc`, `w.thumbs` and so on) keep working. Tests of the title, size, full screen,
slideshow and closing move to the outer window. The teardown hook in `tests/conftest.py` destroys
windows explicitly (*Closing a Qt window does not destroy it*, in `CLAUDE.md`). It must destroy the
outer windows too, and `tests/test_no_widget_leak.py` must still pass.

**Hand check on Windows:** open from File Explorer with the app in the background, full screen,
slideshow, minimise and restore, close with unsaved changes, open on a second monitor, and shrink
the window to its smallest size.

##### M186.2 — KlarPDF draws its own title bar, with one tab

The top strip now shows one tab with the file's name, and its unsaved mark, instead of
`report.pdf — KlarPDF`. KlarPDF draws this strip itself. Today Windows draws it.

Everything the Windows title bar does today must keep working:

- dragging the strip moves the window, and dragging it to a screen edge snaps it there;
- double-clicking the strip maximises and restores the window;
- the edges and corners still resize the window;
- right-clicking the strip shows Windows' window menu;
- on Windows 11, hovering over the maximise button shows the snap layouts. Windows asks a program
  which part of its window is under the pointer, and shows the layouts only when the answer is
  "the maximise button";
- the window keeps its shadow;
- a window in the background looks dimmer than the one in front;
- the strip follows the light or dark theme when Windows switches (M29);
- the strip is the right size at every display scale, including the owner's 1.75× laptop.

The window keeps its title, `report.pdf — KlarPDF`, even though the strip does not show it. The
taskbar, Alt+Tab and screen readers read that title.

**How.** Qt 6.11.1, which we pin, has a window setting that extends the window's contents into the
title bar (`Qt.WindowType.ExpandedClientAreaHint`). Which systems honour it has not been checked.
This part checks it first, on Windows and on WSLg. Qt also has functions that ask the system to move
or resize a window (`QWindow.startSystemMove`, `startSystemResize`), which work on Wayland too. Any
code that only Windows needs goes in `platform_integration.py` (*Keep OS-specific code quarantined*,
in `CLAUDE.md`; Ruff enforces it since M168).

Full screen and slideshow hide the strip with the rest of the chrome.

**If the title bar cannot keep a behaviour above**, the owner decides before this part merges:
accept the loss, or show the row of tabs below the title bar instead.

**To decide when built:** whether the strip shows the app's icon at its left, as Notepad does.

##### M186.3 — several tabs in one window

- A file opened from File Explorer opens as a tab in the front window. The front window is the
  KlarPDF window used last. Qt cannot answer this on its own: `QApplication.activeWindow()` is empty
  while another program has focus, which is exactly when File Explorer hands a file over. So the app
  records which window was used last.
- File ▸ Open and Open Recent open a tab in their own window.
- A file that is already open, in any window: that window comes to the front and that tab comes
  forward.
- Click a tab to bring it forward. Ctrl+Tab and Ctrl+Shift+Tab move to the next and the previous
  tab. Neither key is used in the app today. Check that no panel or text box accepts them first
  (*A key routed "through the view" never arrives if a child widget accepted it*, in `CLAUDE.md`).
- Tabs can be dragged along the row to change their order.
- File ▸ Close (Ctrl+W) closes the tab in front, and asks to save first if it has unsaved changes.
  Closing the last tab closes the window.
- Closing the window asks about each unsaved file in turn, with today's question. Cancel on any one
  keeps the window and all its files open.
- A tab in the back frees its page pictures, as a minimised window does today (M87.2). They are
  drawn again when the tab comes forward.
- A file changed by another program is checked when its tab comes forward.
- Closing a tab destroys its widgets, as closing a window does now. `tests/test_no_widget_leak.py`
  covers it.
- `tests/test_single_instance.py` expects a second launch to open a new window. It now expects a
  new tab.
- `README.md`'s Features list gains tabs in this PR, because this is the change a user sees.
- `PLAN.md` §Future enhancements, *Drop-to-open in the main view*, says a dropped PDF would open
  "as a new window". Change it to a new tab.

**To decide when built:** whether the row of tabs has a **+** button that opens a file.

##### M186.4 — pull a tab out, put it back

- Drag a tab out of the row and drop it away from any KlarPDF window: the file gets its own window.
- Drag a tab onto another KlarPDF window: the file joins that window's tabs. If that was the last
  tab in the old window, the old window closes.
- A tab's right-click menu offers **Move to New Window**.
- A command puts every open file into one window, as Preview's **Merge All Windows** does.

Moving a file to another window moves its page view and sidebar. Three things must hold:

- **The pages are redrawn for the new window's screen.** Two screens can have different scaling,
  and every page picture carries its screen's scaling (M88.2, and *A page picture's width in pixels
  is not its size on screen*, in `CLAUDE.md`).
- **A drag in progress ends first.** Moving the view while a drag is live leaves a dead item in the
  scene (*A drag keeps an item in the scene*, in `CLAUDE.md`).
- **Nothing in the file stays connected to the old window.** Either can outlive the other (*Never
  connect a widget's slot to a signal on a QObject that outlives it*, in `CLAUDE.md`).

Dragging pages between two windows keeps working as it does today. `_on_pages_dropped` finds the
source file through `PdfApp.window_for_key` (`main_window.py:1633`).

On WSLg, Qt runs on Wayland, which does not let a program choose where its windows appear. So a
pulled-out window may not open where the tab was dropped there. Check this by hand on Windows.

**To decide when built:** where the "every file into one window" command goes. `PLAN.md` §Design
budgets, *UI budget*, limits new top-level menus.

#### Options not chosen

- **One menu bar and one toolbar per window, with the tabs below them** (owner, 2026-11-25). The
  owner chose this first, then changed to whole windows in tabs. Reasons:
  - It is the bigger change. `MainWindow` (3,358 lines) would be split into a window part and a
    file part. Its 150 commands would be pointed at the tab in front. 97 of the 168 test files reach
    into a window's parts, about 2,400 times. How many of those would break was not counted.
  - Pulling a tab out costs about the same either way. In both, a file's pages move to another
    window, and that move is the risky part.
  - The menus and toolbars that every tab carries cost little (*What was measured*, above).
  - Tabs above the menus is how Windows 11's Notepad looks.

  What whole windows in tabs gives up: each tab shows its own menus and toolbars, so they can
  differ between tabs, for example when the markup toolbar is open in one tab only. And if the
  shared layout is wanted later, the split is still needed: this plan is not a step toward it.
- **No tabs, and a faster way to switch windows** (a Window menu and Ctrl+Tab between windows).
  Not chosen: the owner wants tabs.
- **Dropping pages onto another file's tab**, to move pages without a second window. Not chosen:
  the owner chose pulling a tab out instead.
- **Hiding the row of tabs when a window has one file.** Not chosen: the tabs take the title bar's
  place, so they cost no space (decision 5).

#### Not in this plan

- **Two files side by side inside one window.** Pulling a tab out gives two windows, and Windows
  Snap can put them side by side.
- **Scrolling two files together while comparing them.** Not asked for.
- **Reopening the last session's tabs at start.** Not asked for. Today a window's size and position
  are deliberately not remembered either (`closeEvent`, `main_window.py:3351`).
